Conclusion and Further Enhancements Conclusion This project set out to build a locally-running, privacy-preserving healthcare qa system that returns grounded answers with calibrated uncertainty estimates. All the main objectives were met. The system retrieves relevant documents from a 505,584-document medical knowledge base in about 43 seconds on CPU, generates an answer in about 70 seconds, and returns a five-signal confidence breakdown and source attribution alongside every response. End-to-end retrieval accuracy on the 36-question gold set is 97.2 %, and keyword coverage of reference answers is 0.3845 with TinyLlama and 0.4634 with the QLoRA fine-tuned adapter. The most consequential design decision was the knowledge base construction method. Switching from flat character-based chunking to sentence-boundary-aware chunking raised keyword coverage by 0.292 points on the dense-retrieval evaluation, a larger gain than any model change or retrieval algorithm change made during the project. Chunking strategy determines what the retriever can find, and what the retriever can find determines the ceiling on answer quality. The confidence scoring module trades raw keyword coverage for calibrated uncertainty. The source agreement signal hedges responses when retrieved sources discuss the same topic from conflicting perspectives, which reduces coverage metrics but produces more honest uncertainty estimates. The ECE of 0.144 indicates room for improvement in calibration; the system is systematically under-confident, which a dedicated calibration set separate from the evaluation set would help correct through proper Platt parameter fitting. Running the full stack on CPU without internet access is practical but slow. 106 seconds on a warm path is acceptable for a research prototype, but the same pipeline on a mid-range GPU would run in under 5 seconds and would change the use-case possibilities considerably. Limitations The evaluation set of 97 questions is small. Confidence intervals for keyword coverage span roughly 0.15 points in each direction, so differences smaller than about 0.05 between system variants are within the noise. A proper evaluation would require at least 500 questions with human-rated answer quality. The system has not been validated by clinical professionals. The knowledge base contains accurate information drawn from research abstracts and real patient-doctor conversations, but the system can still retrieve irrelevant passages and generate plausible-sounding but incorrect answers. The safety guardrail catches obvious dangerous query types, but it is pattern matching, not clinical reasoning. Human evaluation of answer quality was not completed during the project timeline. The template at evaluation/human _eval _template.csv was prepared and is ready for distribution, but collecting responses from qualified reviewers was outside the project scope. The BM25 index rebuild from the 505k-document corpus takes 30--60 seconds if the pickle cache is missing. On machines with limited ram, this can cause out-of-memory failures if the index is built while the embedding model is already loaded. Further enhancements Latency reduction Moving to a machine with a T4 or equivalent GPU would reduce generation latency from 70 seconds to under 2 seconds and retrieval from 43 seconds to under 5 seconds. No code changes are required; both the Transformers and llama-cpp-python backends use GPU automatically when CUDA is available. Continuous knowledge base updates The knowledge base is currently static. A production deployment would benefit from an ingestion pipeline that periodically pulls new PubMed abstracts and clinical guidelines, chunks them with the RecursiveSentenceChunker, and upserts them into ChromaDB. ChromaDB supports incremental upserts; the main cost is regenerating the BM25 index, which would need to run offline during low-traffic periods. Extended multi-turn support Multi-turn conversation with follow-up resolution is implemented across two components. The ConversationManager class maintains session history across queries within a session. Follow-up detection is handled by the FollowUpDetector class in src/ FOLLOWUP REFERENCE _has _clear _subject() test that returns false when a question opens with a reference pronoun but no independent subject starter follows. If any check fires, the question is classified as a follow-up. When a follow-up is detected, the pipeline augments the retrieval query by prepending the prior conversation context: lstlisting[language=Python] retrieval_query = f"{conversation_context question" lstlisting The hybrid retriever therefore searches the knowledge base against the full exchange rather than the new question in isolation. Extending support to longer context windows across many turns, and replacing the _has _clear _subject() heuristic with a lightweight dependency parser, are natural next steps. Clinical validation Deploying in any patient-facing context would require evaluation by licensed medical professionals against established clinical guidelines. The current automated metrics measure textual similarity to reference answers; they do not measure clinical accuracy or safety. Calibration improvement The ECE of 0.144 with systematic under-confidence suggests the Platt scaling parameters were not fitted on a sufficiently large or representative set. A calibration set of at least 300 questions, balanced across the four query categories, would likely produce better-calibrated scores. Temperature scaling~ guo2017calibration is a simpler alternative to Platt scaling that is easier to tune and performs comparably on many classification tasks. Larger evaluation set The 97-question set is sufficient to observe large differences (the 0.292 KB v1-vs-v2 gap is clearly above the noise floor) but not small ones. Extending the gold set to 500 or more questions with human quality ratings would allow more reliable conclusions about differences between model and configuration variants.
