Project Implementation Repository structure The repository has ten top-level directories: itemize src/: Core pipeline modules (retrieval, generation, XAI, safety, utils, data pipeline, LangChain, LangGraph). api/: FastAPI application ( main.py) and demo server. frontend-react/: React frontend using the assistant-ui library. frontend/: Streamlit application retained for evaluation and diagnostic use. evaluation/: Evaluation scripts, gold retrieval data, and results. data/: Knowledge base directories, BM25 cache, audio recordings. config/: Settings module with environment variable driven configuration. tests/: Pytest test suite. scripts/: Utility scripts for profiling, evaluation bundle, and smoke testing. models/: Fine-tuned adapter weights and BioMistral gguf file (not in git). itemize Knowledge base construction Two versions of the knowledge base were built. Version 1 used a flat character-based chunker producing 500-character chunks with no sentence boundary awareness. Version 2, built in Colab Session A on a tpu v5e, used the RecursiveSentenceChunker with a 512-token target size and 64-token overlap. The difference in retrieval quality between the two versions is the single largest performance factor in the evaluation results --- keyword coverage improved by 0.292 points on the same 97-question set. Pipeline implementation Retrieval module src/retrieval/hybrid OrderedDict-based lru cache in the embedding layer ( src/embeddings/embedding _models.py) avoids re-encoding identical query strings, which matters when the query expander generates several variants of the same question. Per-stage timing is recorded in milliseconds via time.perf stage _latencies field of every response. On the test hardware, the retrieval stage (BM25 + dense + RRF) takes a mean of 42.6 seconds, the corrective RAG check adds 1.2 seconds, and generation accounts for 69.9 seconds. Generation module The MedicalLLM class in src/generation/ model tinyllama backend uses HuggingFace Transformers with bfloat16 precision and HuggingFace's TextIterator biomistral backend uses llama-cpp-python with the gguf model file. Both expose streaming via the generate _stream() generator method. Frontend implementation The React frontend in frontend-react/ uses the assistant-ui library for the chat thread component. It calls the /ask/stream endpoint and renders tokens progressively as they arrive. Source cards below the answer display each attributed passage with its relevance score. A diagnostics panel, toggled from the UI, shows the per-stage latency breakdown, confidence signal values, and any hallucination flags. The Streamlit frontend in frontend/streamlit ui for this project. It renders the full response alongside a source attribution panel, a per-stage latency breakdown, confidence signal values, and any raised hallucination flags --- all in a layout that non-technical reviewers can read without additional tooling. The chat history persists within the session, and the sidebar exposes model selection and retrieval-mode controls so the system behaviour can be adjusted without restarting the server. Streamlit's native component model means the entire interface runs off a single Python file with no separate build step, which simplifies deployment to hosted environments such as Hugging Face Spaces. LangGraph implementation src/langgraph/langgraph _pipeline.py wraps the pipeline stages as LangGraph nodes: a start node for safety checking and query enhancement, a retrieval node, a grounding decision node that branches on context sufficiency, a generation node, and a post-processing node for hallucination detection and confidence scoring. The LangGraph path handles multi-hop queries, where a second retrieval round is triggered if the first round returns insufficient context. Deployment figure[!ht] centering images/deployment_architecture_final.png Deployment architecture: GitHub Actions CI pipeline triggers on push to main (lint and test); Docker Compose brings up the FastAPI backend and Streamlit frontend with ChromaDB and the BM25 index persisted on a shared volume. fig:deployment_arch figure The deployment topology for the Explainable Healthcare QA Chatbot is designed to be highly reproducible and to minimize environment-specific discrepancies between local development and production. By containerising both the application logic and the underlying vector database, the system can be deployed to any Docker-capable host with a single command. Docker Compose deployment The system is packaged as a two-service Docker Compose application defined in docker-compose.yml. The api service runs the FastAPI backend; the frontend service runs the Streamlit application. Both services are built from the same repository root using the project Dockerfile. ChromaDB runs embedded within the api container rather than as a separate process: the collection name is fixed to medical data/knowledge_base_v2, mounted as a named Docker volume so the knowledge base survives container restarts. The BM25 index is also stored within the same volume at data/knowledge_base_v2/bm25_index.pkl. Setting SKIP _BM25=true in the Compose environment skips the BM25 index build during the startup warmup pass, which reduces the time before the first request is accepted on hardware where the index is already cached. The complete deployment sequence is: lstlisting[language=bash, caption=Docker Compose deployment] docker-compose up --build lstlisting Health checks on the api service poll /health every 30 seconds. The frontend service declares a depends api health check, so Streamlit does not start until the FastAPI backend has loaded the model and passed its first health probe. Continuous integration The GitHub Actions workflow in .github/workflows/ci.yml runs on every push to main and on pull requests. It installs CPU-only PyTorch to avoid downloading the 2 GB GPU build on the CI runner, runs flake8 linting, and executes the pytest suite with the -k "not langsmith" filter to skip tests that require a LangSmith api key. Docker layer caching keeps the CI build under 10 minutes. This continuous integration pipeline acts as the primary gatekeeper for code quality. By strictly enforcing that all new commits pass the validation suite before they can be merged into the main branch, the repository maintains a high standard of reliability. Furthermore, by heavily utilizing cache-to and cache-from directives within the GitHub Actions runner, the pipeline avoids recompiling heavy native dependencies like llama-cpp-python on every run. In future iterations, this pipeline could be expanded to include automated deployment hooks (Continuous Deployment) that push the validated Docker images directly to a container registry, such as GitHub Container Registry or AWS ECR. From there, a production server could automatically poll the registry and perform rolling updates on the running Compose cluster, effectively achieving zero-downtime deployments for the RAG chatbot.
